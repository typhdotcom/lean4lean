# Divergences from the Lean Kernel

This is a list of places where lean4lean deliberately has different behavior from the kernel. Unless specified here, any divergence between lean4lean and [lean4](https://github.com/leanprover/lean4/tree/master/src/kernel) is a bug.

* [`Lean4Lean.TypeChecker.Inner.reduceNative`](Lean4Lean/TypeChecker.lean): Lean4lean does not support reduction of `reduceBool`. This would involve implementing verified compilation, which while possible would be an additional chunk of work comparable to this entire repo.
* [`Lean4Lean.Primitive.checkDef`](Lean4Lean/Primitive.lean), `checkInductive`: Lean does not check that primitives are declared with the correct types and definitional behavior, except in the case of `Eq` which is used in the declaration of `Quot`. This is required for soundness, but Lean is able to get away with it because Lean ships its prelude and using an alternative prelude is not supported.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), literal case: The original code was not checking that the literal type actually exists. Again, this is okay provided that the prelude is trusted.
* [`Lean4Lean.TypeChecker.Inner.tryStringLitExpansionCore`](Lean4Lean/TypeChecker.lean): there is a counterproductive `whnf` call in this function which is removed in Lean4lean.
* [`Lean4Lean.TypeChecker.Inner.isDefEqApp`](Lean4Lean/TypeChecker.lean): lean4lean compares the two argument counts before the two heads, where `type_checker::is_def_eq_app` compares the heads first. Both answer `false` when the counts differ, so the decision is the same.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), application case: lean4lean checks `isDefEq dType aType`, where `infer_app` checks `is_def_eq(a_type, d_type)`. Definitional equality is symmetric, so this cannot change the answer, but this avoids some needless left-right flipping.
* [`Lean.Level.normalize`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Level.lean), `isEquiv`, `geq`, `instantiateLevelParams`: Lean4lean uses the level operations from Lean's standard library, which differ from the C++ kernel's; [leanprover/lean4#14356](https://github.com/leanprover/lean4/pull/14356) tracks aligning them. This has two separate consequences. The comparison operations decide slightly different sets of (in)equalities than the kernel's `is_equiv`/`is_geq` (but see the next point). And because `instantiateLevelParams` builds levels with `mkLevelMax'`/`mkLevelIMax'` rather than the kernel's `mk_max`/`mk_imax`, unfolding a universe-polymorphic constant can produce a term that means the same as the kernel's but is not syntactically equal to it, and so does not share its `Expr.hash`.
* [`Lean.Level.normalize'`](Lean4Lean/Level.lean), `isEquiv'`, `geq'`: Lean4lean implements a new algorithm for level normalization. These run the standard library's operation as a fast path and fall back to a complete decision procedure for level algebra, so lean4lean decides level equality and `≥` for *more* pairs than either the standard library or the kernel — it accepts declarations the kernel rejects for reasons of level incompleteness, never the other way around.
* [`Lean4Lean.checkConstantVal`](Lean4Lean/Environment.lean): The original implementation would call `check` which sets the level params and then unsets them afterward, and then `ensure_sort` would run in a context without any level params. In lean4lean the monad is parameterized over level params, so they remain the same across the two calls.
* [`Lean4Lean.TypeChecker.Inner.inferProj`](Lean4Lean/TypeChecker.lean), [`toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean): both kernels recognize `Prop` up to universe normalization ([leanprover/lean4#14613](https://github.com/leanprover/lean4/pull/14613)), but they differ on levels that are neither always nor never zero: lean4lean tests `isNeverZero` where Lean tests `!isAlwaysZero`. Lean4lean's rule keeps `Expr.proj` no more powerful than the recursor the kernel generates for the same type. For `MaybeProp.{u} : Sort u` with a field in `PUnit.{u}`, the kernel cannot rule out that the type is a proposition, so it emits `MaybeProp.rec : {motive : MaybeProp → Prop} → ...` — small elimination only — and `fun x => x.0 : MaybeProp.{u} → PUnit.{u}` cannot be written with it. Lean accepts that projection anyway, so under Lean's rule `proj` computes something the type's own eliminator cannot. Lean's choice is still sound, but only because the constructor universe bound in `inductive.cpp` separately rejects `inductive T.{u} : Sort u where mk : Bool → T`, which would otherwise give an analogue of the construction in #14613; testing `isNeverZero` makes the projection check independent of that bound. Reconciling the two in the other direction — letting the recursor eliminate large whenever every field's universe is bounded by the inductive's, which is exactly what makes such a projection sound — would be the complete answer, but that is a change to recursor generation rather than to this check.
* [`Lean4Lean.Environment.addInductive`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621) rechecks the declarations produced by nested-inductive elimination — the restored constructor types, the restored recursor types and the recursor rules' right-hand sides — in the finished environment. Lean4lean checks the restored terms that contain a `let`, against the block's constants added as axioms in the order the model adds them, and rejects a restored term that still mentions an auxiliary constant; the other restored terms are proved well typed rather than rechecked. The check of the nested applications `I Ds` from [#14577](https://github.com/leanprover/lean4/pull/14577) is kept, against the block's types as axioms rather than in the finished environment: those arguments are dropped from the auxiliary declarations, so checking the block does not cover them, and they cannot mention the block's recursors.
* [`Lean4Lean.checkClosed`](Lean4Lean/Inductive/Add.lean): lean4lean rejects an inductive declaration whose type or constructor types have loose bound variables. Lean's kernel opens a constructor's parameters with `instantiate1`, which lowers a loose variable, and closes them again without raising it, so the variable is captured by a parameter binder, in flat and nested blocks alike: it accepts `LooseFlat.mk : ∀ α, #1 → LooseFlat #1` and stores `(α : Type) → α → LooseFlat α`, and `LooseTree.mk : ∀ α, List (LooseTree α) → #2 → LooseTree α` as if the third binder's type were `α` ([`Tests/NestedInductive.lean`](Lean4Lean/Tests/NestedInductive.lean)). The stored type is not the declared one. No elaborated declaration has loose bound variables; replaying Lean's core library and lean4lean's modules gives the same verdicts.
* [`Lean4Lean.Environment.addInductive`](Lean4Lean/Inductive/Add.lean), auxiliary names: lean4lean rejects a constructor type that names one of the auxiliary types or constructors the elimination made, whatever its name. `checkNoNestedAux` (below) rejects names under `_nested`, but the auxiliary type for a nested occurrence of a type named `Name.anonymous`, which both kernels accept, is `_nested_1`, outside that namespace. Lean's kernel accepts `AnonUse.bad : _nested_1 → AnonUse` alongside `AnonUse.mk : «» AnonUse → AnonUse`, though no constant `_nested_1` exists, and stores `bad : «» AnonUse → AnonUse` ([`Tests/NestedInductive.lean`](Lean4Lean/Tests/NestedInductive.lean)). No elaborated declaration names an auxiliary constant; replaying Lean's core library and lean4lean's modules gives the same verdicts.
* [`Lean4Lean.checkNoNestedAux`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14616](https://github.com/leanprover/lean4/pull/14616) rejects the reserved `_nested` prefix in both the inductive types and the constructor types of a declaration; lean4lean checks only the constructor types. The bug that check fixes is specific to constructors: nested occurrences are rewritten to the auxiliary types in constructor types only (`replaceAllNested`), and rewritten back the same way (`restoreNested`), so an inductive's own type is carried through both directions verbatim and cannot acquire a type it was not checked at. A `_nested` name written in an inductive type also cannot resolve in the first place: the auxiliary types are declared in the same block, so they are not in the environment while that block's types are checked (unlike constructor types, which are checked once the block's types, auxiliaries included, are present), and they never survive into the final environment. Lean's check additionally reserves the whole `_nested` namespace against unrelated user declarations, which lean4lean does not.
* [`Lean4Lean.ElimNestedInductive.Result.restoreNested`](Lean4Lean/Inductive/Add.lean), `restoreCtorName`: Lean's kernel opens the term's parameter binders and replaces each application headed by an auxiliary constant with the nested occurrence at those parameters, at the block's levels, keeping the application's remaining arguments as they are. Lean4lean replaces an auxiliary constant where it is applied to exactly as many arguments as the block has parameters, by the occurrence at those arguments and at the constant's own levels (instantiated without simplifying them), and restores the remaining arguments too. Every auxiliary application the elimination produces is at the outer parameters and levels with no auxiliary constant among its other arguments, so both give the same terms; replaying Lean's core library and lean4lean's modules gives recursors identical to Lean's. [leanprover/lean4#14632](https://github.com/leanprover/lean4/pull/14632) turned the `lean_assert`s in the restoration into kernel exceptions; lean4lean's restoration has no failing branch, and a term it leaves an auxiliary constant in is rejected (see the previous point). Earlier versions of this restoration instantiated the occurrence's levels with simplification, and looked through metadata in an application's head and dropped it, which Lean's kernel keeps: for a field of type `mdata (List T)`, or an occurrence at `List.{max u u}`, the recursors differed from Lean's ([`Tests/NestedInductive.lean`](Lean4Lean/Tests/NestedInductive.lean) checks both).
* [`Lean4Lean.AddInductive.stripAnnotations`](Lean4Lean/Inductive/Add.lean): when an inductive block's binders are opened, both kernels strip the type annotations `optParam`, `autoParam`, `outParam` and `semiOutParam` from their types by name. That keeps the binder's type only if the environment defines the annotation as returning its first argument, as Lean's prelude does. Lean's kernel does not check this; lean4lean checks, for each annotation it strips, that the environment has it as a safe definition `fun x₁ … xₖ => x₁`, and rejects the block otherwise. A prelude whose `optParam` returns its second argument shows the difference: Lean accepts a constructor `I.mk : optParam N I → I` with `I.rec : (∀ x : N, motive x → motive (I.mk x)) → ∀ t, motive t`, where `motive x` is ill-typed, and lean4lean rejects it ([`Tests/Annotations.lean`](Lean4Lean/Tests/Annotations.lean)). So does a block that declares a type under one of these names and uses it in a binder. With Lean's prelude every check passes, and replaying Lean's core library and lean4lean's modules gives the same verdicts and recursors as before this change.
* [`Lean4Lean.AddInductive.getIIndices`](Lean4Lean/Inductive/Add.lean): when the recursor is built, a field `isRecArg` saw as recursive gets an inductive hypothesis built from its type with type annotations stripped, normalized again. If that no longer ends in a type of the block, Lean's kernel only `lean_assert`s; a release build uses the block's first type and its arguments as indices, and accepts an ill-typed recursor. Lean4lean rejects the block. An annotation that is not the identity would reach this, as above, but lean4lean rejects those first; with annotations that are, stripping commutes with normalization, so the two agree.
* [`Lean4Lean.Environment.checkName`](Lean4Lean/Environment/Basic.lean): lean4lean rejects a declaration named `_inhabitedExprDummy`. That is the constant `default : Expr` is, which lean4lean's kernel returns from a panic (an out-of-bounds `!` access, `unreachable!`); with no declaration of that name, such a term fails to type check rather than standing for something. Lean's kernel, in C++, has no such value and accepts the name. No declaration in Lean's core library or lean4lean's modules uses it.
* [`Lean4Lean.checkEqType`](Lean4Lean/Quot.lean): lean4lean refuses to initialize quotients when `Eq` is an unsafe inductive. The quotient constants are safe and `Quot.lift`'s type mentions `Eq`, so with an unsafe `Eq` safe constants would depend on an unsafe one, which the kernel rejects everywhere else. Lean's kernel checks `Eq`'s shape but not its safety, and accepts such a prelude ([`Tests/UnsafeEq.lean`](Lean4Lean/Tests/UnsafeEq.lean)). Lean's prelude declares `Eq` safe; replaying Lean's core library and lean4lean's modules gives the same verdicts and output before and after this check.
* [`Lean4Lean.TypeChecker.Inner.tryEtaStructCore`](Lean4Lean/TypeChecker.lean): for a structure that may be a proposition (its sort is not never zero), lean4lean declines structure eta unless every field of the constructor application is a proof. Such a structure's other projections are not typed (`inferProj` refuses them), and Lean's kernel compares them with the constructor's arguments anyway, inferring their types without that check; lean4lean, whose projection inference always checks, threw an invalid projection error there. The comparison of an untyped projection can only fail, so both kernels reject the same declarations, with the same error ([`Tests/MaybePropEta.lean`](Lean4Lean/Tests/MaybePropEta.lean)); replaying Lean's core library and lean4lean's modules gives the same verdicts and output before and after this check.
* [`Lean4Lean.TypeChecker.Inner.reduceProjCore`](Lean4Lean/TypeChecker.lean): lean4lean reduces a projection only out of a constructor applied to exactly its parameters and fields, where Lean's kernel takes the field from any application with enough arguments. A typed projection's structure that is a constructor application always has exactly that many, so this changes nothing on typed terms; replaying Lean's core library and lean4lean's modules gives the same verdicts and output before and after this check.
* [`Lean4Lean.quotReduceRec`](Lean4Lean/Quot.lean): lean4lean reduces `Quot.lift f h (Quot.mk r' a)` and `Quot.ind` only when the constructor's type and relation are definitionally equal to the eliminator's, where Lean's kernel reduces on any `Quot.mk` application with three arguments. A typed eliminator's quotient argument always passes, so this changes nothing on typed terms; replaying Lean's core library and lean4lean's modules gives the same verdicts and output before and after this check.
* [`Lean4Lean.inductiveReduceRec`](Lean4Lean/Inductive/Reduce.lean): lean4lean reduces a recursor only on a constructor applied to exactly its parameters and fields, where Lean's kernel needs only as many arguments as fields. A typed major premise that is a constructor application always has exactly that many, so this changes nothing on typed terms; replaying Lean's core library and lean4lean's modules gives the same verdicts and output before and after this check.
* [`Lean4Lean.toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean): when the major premise's type's type does not normalize to a sort, lean4lean leaves the major premise unchanged, where Lean's kernel expands it by structure eta unless it normalizes to `Prop`. On a typed term it always normalizes to a sort, so this changes nothing there; replaying Lean's core library and lean4lean's modules gives the same verdicts and output before and after.
* [`Lean4Lean.TypeChecker.Inner.inferProj`](Lean4Lean/TypeChecker.lean): lean4lean rejects a projection whose index is not below its constructor's number of fields before walking the constructor's type, where Lean's kernel walks on and fails when the type it reaches is not a pi. Past the last field that type is the structure's application, so both reject with the same error; replaying Lean's core library and lean4lean's modules gives the same verdicts and output before and after this check.
* [`Lean4Lean.FuelConfig`](Lean4Lean/FuelConfig.lean): since [leanprover/lean4#13956](https://github.com/leanprover/lean4/pull/13956), the native kernel bounds mutually recursive checking through the `maxRecDepth` option. Lean4lean exposes several independent fuel counters instead, because its Lean definitions also need explicit termination witnesses. Replay comparison therefore uses each implementation's default bound unless an explicit lean4lean fuel configuration is supplied.
* [`Lean4Lean.addDefinition`](Lean4Lean/Environment.lean) (`unsafe` branch), [`addMutual`](Lean4Lean/Environment.lean): an `unsafe`/`partial` definition may be recursive, so its body is checked in an environment that already contains the declaration. The C++ kernel adds `constant_info(d)` there -- the full definition, value included -- so the body can delta-unfold the very constant being defined. Lean4lean adds it as an axiom of the same type instead: the body may still *refer* to the block's constants, but cannot unfold them. So for example `unsafe def foo : Nat := (fun (_ : foo = 1) => 1) rfl` is accepted by the C++ kernel, but rejected by L4L: checking the argument requires `foo =?= 1`, which succeeds by unfolding `foo` to its own body and reducing. Read literally, that rule makes a typing fact about the constant available while establishing it, and implementing this in `IsDefEq` directly degenerates completely, allowing even things like `unsafe def bar : Nat := "hi"` by using the typing judgment to justify itself. The gap is confined to `unsafe`/`partial` code, which carries no logical content.
* [`Lean4Lean.addMutual`](Lean4Lean/Environment.lean): lean4lean requires the declarations of a mutual block to carry the same universe parameters and to have distinct names. Both checks are in kernel PRs that are not yet released ([leanprover/lean4#14608](https://github.com/leanprover/lean4/pull/14608), [#14632](https://github.com/leanprover/lean4/pull/14632)); the released kernel checks only that the safety annotations agree. Lean4lean needs them rather than merely matching them: the block is checked under a single `M.run`, whose level parameters are fixed for the whole run, and the model adds the block's constants one at a time with `VEnv.addConsts`, which fails on a repeated name.
* [`Lean4Lean.AddInductive.run`](Lean4Lean/Inductive/Add.lean), `declareTypeAxioms`: lean4lean checks an inductive block's constructors, and computes its elimination level and recursors, in an environment where the block's types are axioms, and builds the recursors with its constructors as axioms too (for the primitive `Bool` and `Nat`, whose shape is fixed, their constructors too, since the primitive invariant asks for a primitive type's constructors to come with it; a clash with those names is then reported before the constructors are checked rather than when they are declared). The kernel uses one where they are already inductive types, with the constructors declared too once they have been checked. The block is added to the original environment either way, so the result is the same. This is how `addMutual` checks a mutual block, and it is the environment that `addInductive.WF_flat`, the verification of `addInductive`, models: the type checker's rules for inductive types assume that an inductive type's constructors and recursor exist. The two environments behave differently only where checking compares terms of a block type:
  * `isDefEqUnitLike` on a block type with a single fieldless constructor: both kernels look the constructor up with `get` and throw "unknown constant" while checking constructors; lean4lean returns false and the comparison carries on. So lean4lean may accept a declaration that both kernels reject. It accepts more, never less. This is sound because axioms have fewer definitional equalities than inductive types; what establishes it is `addInductive.WF_flat`, which is not yet proved.
  * `inferProj` on a block type inside a constructor type fails with `invalidProj` instead of throwing "unknown constant".
  * While the recursors are built (`mkRecInfos`, `declareRecursors`), a type checker call that meets one of the block's constructors finds an axiom, where the kernel finds a declared constructor. A constructor constant has no definitional behavior of its own: iota, structure eta, K-like reduction and unit-like defeq all go through its type's inductive declaration, which is an axiom here as in the cases above. So this changes no verdict beyond those cases. Without the axioms such a call would throw "unknown constant"; with them it can only reach the kernel's verdict, never reject where the kernel accepts.
  * An unsafe block's constructors are not checked for positivity, so its fields are first weak-head normalized while its recursors are built. With the constructors declared, `isDefEqUnitLike` could succeed there (inside K-like reduction); with axioms it does not, so such a field is seen less reduced, and possibly as not recursive. A safe block that reaches this case is rejected while its constructors are checked, in both kernels.

  Replaying Lean's core library (Init, Std, Lean, Lake) and lean4lean's own modules from scratch accepts the same declarations before and after this change (some 200,000 each, of which about 3,000 inductive blocks; the replay skips unsafe and partial declarations), and the recursors generated match Lean's. The same holds for building the recursors with the constructors as axioms: 203,350 declarations (3,038 inductive blocks) from Lean's core library and 204,059 (3,000) with lean4lean's modules, all accepted before and after, with identical output and every recursor equal to Lean's.
* [`Lean4Lean.TypeChecker`](Lean4Lean/TypeChecker.lean), `withFreshId`: on leaving a binder, lean4lean restores the equivalence manager and the inference and `whnf` caches to what they were on entering it; Lean's kernel keeps them for the whole declaration. An equivalence or a check established under a variable may depend on it without mentioning it: with `I : (n : B) → A n → Prop | mk (x : A b0) (h : P x) : I b0 x` and `F a h := I.rec (fun _ _ => b0) h`, the equivalence manager learns `C (F a hI) ≡ C b0` under `p : P a` (through `C (F a (I.mk a p))`, using proof irrelevance), and Lean's kernel then accepts `c : G b0` for `c : C (F a hI)` outside `p`, where no derivation of it in the type theory is known; with only the equivalence manager restored, a check of `c : G b0` cached under `p` is reused outside it. Lean accepts both declarations and lean4lean rejects them ([`Tests/BinderScope.lean`](Lean4Lean/Tests/BinderScope.lean)). Replaying Lean's core library and lean4lean's modules gives the same verdicts.
